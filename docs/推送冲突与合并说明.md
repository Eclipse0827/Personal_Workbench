## 二、最可能遇到的冲突，按发生概率排序

### 冲突 1：想切回 `main` 继续干，被工作区挡住（几乎必然发生）

```bash
git switch main
# error: Your local changes to the following files would be overwritten by checkout
```

原因：`main` 停在 `d178da4`，当前分支停在 `ad5a973`，这两个提交里 `server/server.js`、`public/js/views/chat.js` 等 30 多个文件内容不同；而你手上还有一堆未提交的改动，Git 不敢覆盖。

**正确顺序**（不要先切分支）：

```bash
git switch -c release/2.0.0     # 从当前位置拉分支，工作区原样带过去
git add -A && git commit -m "..."
git branch -f main release/2.0.0   # 让 main 直接指到新提交
git push origin main
```

`git branch -f` 不碰工作区，所以不会冲突。前提是 `main` 确实是当前提交的祖先——这里成立（`d178da4` → `ad5a973` → 新提交），是快进，不是重写。

三条旧分支与这次提交重叠 **21 个文件**，重叠度这么高，直接 `git merge` 会很难看：

| 服务端 | `server/server.js`、`server/db.js`、`server/selftest.js` |

**为什么会撞**：旧分支做的是"产品形态再设计"（新增 `docs/product-shape-and-roadmap.md`、`docs/usability-and-competitive-analysis-2026-11.md`），改的是同一批样式与视图；这次做的是桌面/安卓打包与浮窗重构，也改这批文件。两边动的不是同一行，但都在同一个函数里。

**建议的处理方式：不要整分支合并，按文件挑。**

```bash
# 只看旧分支里那些"这次没有对应物"的新文件，先安全拿走
git checkout wip/hand-merge-20261107 -- docs/
git checkout wip/hand-merge-20261107 -- docs/visuals/

# 其余 21 个重叠文件，逐个 diff 人工看，只挑逻辑，不做整文件覆盖
git diff release/2.0.0 wip/hand-merge-20261107 -- public/js/views/dashboard.js
```

整分支 `merge` 的唯一合理时机：确认旧分支只是"文档 + 少量样式"，且你能接受样式回退。否则会出现"刚调好的界面被旧版本盖回去"。

### 冲突 3：换行符造成"整文件都改了"（最容易误判）

现状：

```bash
git config core.autocrlf   # true
git ls-files --eol public/js/app.js
# i/lf  w/crlf  → 索引里是 LF，工作区是 CRLF
```

`core.autocrlf=true` 在 Windows 上是合理的，但它有个副作用：如果哪天换到 macOS / Linux 改同一个文件，或者用了别的 Git 客户端，**同一份代码会被识别成"每一行都变了"**，`git diff` 一片红，实际逻辑没动。

这次已加 `.gitattributes` 兜住：

```
* text=auto eol=lf
*.bat text eol=crlf
*.ps1 text eol=crlf
```

要注意的是：**不要顺手执行 `git add --renormalize .`**。它会按新规则重写所有已跟踪文件的行尾，产生一个几千行的"无意义提交"，之后所有分支合并都要在这个提交上再撞一次。当前索引已经是 LF，不需要这么做。

## 三、真冲突了，怎么下手

```bash
git status                              # 先看是哪种冲突
git diff --name-only --diff-filter=U    # 只列冲突文件
```

三种标记，三种解法：

| 标记 | 含义 | 处理 |
|---|---|---|
| `UU` both modified | 两边都改了同一处 | **必须手改**，没有捷径 |
| `DU` deleted by us | 你删了，对方改了 | 先判断：功能是不是已经用别的方式重写了？是 → `git rm`；否 → `git checkout --theirs` 拿回来 |
| `UD` deleted by them | 对方删了，你改了 | 反向判断，同上 |

这次就有一个现成的 `DU` 候选：`public/js/views/chat-list.js` 已被删除（对话列表逻辑并进了 `chat.js`）。若旧分支还在这个文件里加东西，合并时会报 `DU`——**不要恢复这个文件**，把它的改动手工搬进 `chat.js` 对应位置，然后 `git rm public/js/views/chat-list.js`。

取值判断表（按领域）：

| 领域 | 偏向哪边 | 理由 |
|---|---|---|
| 样式 `public/css/*` | 取这次（release/2.0.0） | 这次重做了视觉体系，旧分支的样式是上一版 |
| 视图 `public/js/views/*` | 逐行看 | 两边都改过交互，按功能挑 |
| `server/*.js` | 逐行看 | 这次加了浮窗通道与多供应商，删了会有功能缺失 |
| `docs/` | 取旧分支 | 这次没动 `docs/`，那边是唯一来源 |
| `README.md` | 手工拼 | 65 KB，两边都大改过，建议以这次为主，把旧分支独有章节补进去 |
| `package.json` | 手工拼 | 只合并 `scripts` 与 `dependencies` 两个块，别整块覆盖 |

## 四、四种"看起来像冲突、其实不是"的情况

1. **`git push` 被拒，提示 `non-fast-forward`**：不是冲突，是远程有新提交。`git pull --rebase` 后重推，不要 `--force`。
2. **`warning: LF will be replaced by CRLF`**：只是提示，不是错误，可以忽略。
3. **中文文件名显示成 `\346\226\207\344\273\266`**：`core.quotepath` 默认转义。执行 `git config --global core.quotepath false` 就能正常显示。
4. **`git status` 里出现一堆 `?? .tmp-*`**：`.gitignore` 已覆盖，如果仍出现，说明规则拼错了，用 `git check-ignore -v <路径>` 查是哪条规则命中。

## 五、绝对不要做的四件事

| 禁止 | 后果 |
|---|---|
| `git push --force origin main` | 覆盖远程历史，任何已克隆的副本都合不回来 |
| `git rm -r --cached .` 再 `git add -A` | 所有文件的删除+新增，历史彻底断掉 |
| 把 `mobile/keystore/` 或 `keystore.properties` 提交上去 | 密钥一旦进历史，删文件也没用，必须**重新生成密钥**并换包 |
| 把 `data/` 加进来"顺便备份" | 75 MB 个人笔记公开；且以后每次推送都要处理这批文件 |

如果第一条已经发生在别的分支上，补救用 `git push --force-with-lease`，并在群里通知所有克隆过的人重新拉。

## 八、怎么把成果交给对方合并（分支多不影响这件事）

### 8.1 先放下那个担心：分支不会跟着你走

Git 的分支是**本地指针**，只有你显式 `git push` 过的才会出现在远程。当前远程只有一条：

```bash
git ls-remote --heads origin
# refs/heads/main   4b4dd42
```

剩下五条（`integrate/upstream-main`、`refactor/simplify-surfaces`、`wip/hand-merge-20261107`、
`integrate/upstream-main-v2`、`redesign/desktop-shell`）**仍然只在你本机**。
对方克隆下来看到的只有 `main`，不会看到你的试错过程。

**只有一种操作会把它们全送出去**：`git push --all` 或 `git push origin --mirror`。别用。

### 8.2 三种交付方式，按对方的情况选

| 对方的仓库 | 用什么方式 | 对方要做什么 |
|---|---|---|
| 就是你现在这个仓库（他有写权限） | 你推分支，他合 | `git merge release/2.0.0` 或直接 `git pull` |
| 他有自己的主仓库，和你的仓库**有共同祖先** | 你 fork，然后开 Pull Request | 在网页上点 Merge |
| 他的主仓库和你的**没有共同祖先**（两套独立历史） | 先 rebase 到他的基上，再 PR；或直接给 patch | 应用 patch 或合并分支 |

### 8.3 情形一：他直接合你的分支（最省事）

对方只需要三条命令：

```bash
git remote add chendi https://github.com/chendi126/Personal_Workbench.git
git fetch chendi
git merge chendi/main          # 上游 main 是它的祖先，这步是快进，不会有冲突
```

他不用管你本地有几条分支，`fetch` 只会拿到远程那一条。

### 8.4 情形二：开 Pull Request（有共同祖先时最规范）

1. 在 GitHub 上 fork 对方的主仓库（如果还没有 fork）。
2. 把这次的提交搬到你 fork 的一条分支上——**关键是这条分支要基于对方的 `main`**：

```bash
git remote add upstream <对方主仓库地址>
git fetch upstream
```

更稳的做法是直接把整段改动"贴"到对方的基上，而不是合并两套历史：

```bash
# 1. 记住这次提交
git branch backup/before-rebase

# 2. 把提交搬到对方 main 之上
git rebase --onto upstream/main ad5a973 release/2.0.0

# 3. 如果有冲突，逐个解决后 git rebase --continue
# 4. 推到自己的 fork
git push -u <你的 fork remote> release/2.0.0
```

3. 在 GitHub 上开 PR：`base` 选 `Eclipse0827/Personal_Workbench` 的 `main`，
   `compare` 选 `chendi126/Personal_Workbench` 的 `main`。
4. 对方看到的是**一个 PR、一条分支、5 个提交**，看不到你本地的五条试错分支。

### 8.5 情形三：两套历史完全无关（比赛交作品常见）

如果对方仓库的第一次提交和你的 `d178da4` 毫无关系，GitHub 会拒绝开 PR——它找不到共同祖先。
两个解法，选一个：

**A. 让对方允许合并无关历史**（他执行，你只需推分支）

```bash
git merge --allow-unrelated-histories <你的分支>
```

**B. 生成 patch 交给他**（最不容易出错，也不暴露任何历史）

```bash
# 你这边：以 ad5a973 为界，把这次的改动打成一个补丁
git format-patch ad5a973..release/2.0.0 --stdout > huanyihuan-2.0.0.patch
```

```bash
# 他那边：在自己的 main 上应用
git am huanyihuan-2.0.0.patch
```

`git am` 会把你的提交原样落到他的历史上，作者信息保留，冲突处理方式和普通合并一样。
补丁文件约 1 MB，微信/邮件都能传。

### 8.6 如果只想给一个"干净的一次性提交"

担心历史里那两个旧提交（`d178da4`、`ad5a973`）看起来乱，可以把整段改动压成一个提交再交：

```bash
git switch -c release/2.0.0-squashed origin/main
git merge --squash release/2.0.0
git commit -m "缓一缓 2.0.0：桌面端、安卓端与参赛材料"
```

这条分支的父提交就是 `origin/main`，只有一个提交、一份完整 diff，最适合放进别人的主仓库。
原来的 `release/2.0.0` 保留不动，方便你自己回看每一步。

> 需要合并的分支：`main`（`4b4dd42`，远程只有这一条）
>
> ```bash

>
> 你这个仓库的 `main`（`fa86042`）是它的祖先，所以这一步是**快进合并，不会冲突**；
> 也可以在网页上直接开 PR：base 选 `Eclipse0827:main`，compare 选 `chendi126:main`。
>
> 仓库里不含安装包与个人数据：exe/apk 超过 100 MB 放不进去，请在本地用 `npm run dist` 与
> `npm run dist:android` 重新构建，签名文件见 `submission/project/README.md`。
