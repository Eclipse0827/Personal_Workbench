## 一、一句话结论

这次要推的是"**能看懂、能复现、能重新构建**"的那部分：
源码、构建脚本、打包配置、参赛文档与配图。
不推的是"**能重新生成**"和"**只属于这台机器**"的那部分：
exe / apk、`node_modules`、安卓构建中间产物、本机学习数据、截图中间图、工具缓存。

判断标准只有两条：

1. 推上去之后，别人 `npm install && npm run dist` 能不能得到同样的东西？能 → 不推产物。
2. 这个文件里有没有只属于本机的东西（个人数据、签名口令、缓存索引）？有 → 不推。

## 四、三个边界判断，说明一下为什么这么切

**1. 为什么 docx 和 pdf 都推，但 exe 不推？**
前两者各 1–3 MB，Git 完全吃得下，评审直接点开就能看；exe 单个就超 GitHub 上限，硬推会被服务器拒绝，而且它只是源码的编译结果。

**2. 为什么 `mobile/` 只推 4 个文件？**
`mobile/` 目录 2.9 GB，其中 2.9 GB 全是 `android/` 与 `node_modules/`。真正需要版本管理的只有 Capacitor 配置和那层 Node 启动壳。已用 `mobile/android/`、`mobile/www/`、`mobile/keystore/` 三条规则把其余部分挡住。

**3. 为什么 `.demo-data/` 不推，但 `seed-demo-data.py` 推？**
数据是脚本的产物，脚本才是知识。留着脚本，谁都能生成一模一样的截图场景；留着数据，只会让仓库里多一份"看起来像真的、其实是假"的样本。

## 五、执行步骤

```bash
# 1. 从当前提交（= origin/main）拉一条发布分支，不直接在 main 上堆
git switch -c release/2.0.0

# 2. 按 .gitignore 收进暂存区，先看一遍
git add -A
git status --short

# 3. 提交
git commit -m "feat: 桌面端与安卓端打包、浮窗同进程、多供应商配置，附参赛材料"

# 4. 推分支
git push -u origin release/2.0.0

# 5. main 快进到这个提交，让默认分支也是最新
git branch -f main release/2.0.0
git push origin main
```
